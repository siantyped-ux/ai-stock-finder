# 주식 트랙 가중치 재조정 — filing 0.30 → 0.20, value 0.20 → 0.30

2026-09-07 작성. 대상: `stock_finder.calc_total` 의 주식 네 축 가중치.

## 왜 이 문서가 있나

"BUY 가 너무 많이 나오니 점수를 조이자" 에서 출발한 조사였다. 조사 결과가
전제와 달랐다 — **BUY 개수는 느슨하지 않고(전체의 1.5%), 문턱을 올려도 더
나은 종목이 남는다는 증거가 없다.** 총점 자체에 예측력이 없기 때문이다.

원인을 축 단위로 분해하니 한 축이 일관되게 해롭고 한 축만 일관되게 이로웠다.
이 문서는 그 한 가지만 고친다.

**이 문서를 미리 쓰는 이유는 ETF 밴드 때와 같다.** 기준선과 트립와이어를
사후에 정하면 나온 결과에 맞춰 기준이 움직인다. 특히 이번 변경은 기대 이득이
작아서(아래 참조), 나중에 "좋아졌다" 를 자유롭게 정의할 여지를 남기면 안 된다.

## 측정 — 축별 예측력

`forward_returns.py` 와 같은 방식이다. 아카이브 각 행의 `bar_date` 로부터 n
거래일 뒤 종가 수익률을 구하고, 축 값과의 Spearman 순위상관을 잰다. 일봉은
`.cache/recompute_frames.json`(2026-09-02 자)을 쓴다.

표본: 5일 n=26,611 · 10일 n=19,677. 기간 분할 기준일 2026-08-19
(전반 19,400 / 후반 7,211, 10일은 19,381 / 296).

| 축 | 가중치 | rho 5일 전/후반 | rho 10일 전/후반 | 4칸 판정 |
|---|---|---|---|---|
| tech | 0.30 | -0.066 / **+0.022** | -0.038 / -0.061 | 부호 뒤집힘 |
| flow | 0.20 | -0.008 / **+0.027** | +0.013 / +0.062 | 부호 뒤집힘 |
| **filing** | **0.30** | -0.080 / -0.016 | -0.058 / -0.118 | **전부 음수** |
| **value** | 0.20 | +0.033 / +0.106 | +0.085 / +0.066 | **전부 양수** |
| total | — | -0.057 / **+0.056** | -0.011 / -0.029 | 부호 뒤집힘 |

극단 구간이 더 선명하다.

```
filing 70-79 :  5일 -1.23% (승률 39)   10일 -2.93% (승률 30)
value  70-79 :  5일 +0.92% (승률 54)   10일 +1.64% (승률 56)
```

가중치의 60%(tech 0.30 + filing 0.30)가 무신호이거나 역신호이고, 유일하게
방향이 유지되는 value 가 20%다. 총점에 우위가 없던 이유가 이것이다
(`forward_returns.py` 기준 BUY 계열의 값어치: 5일 -0.37%p · 10일 +0.13%p,
후자는 표준오차 ±0.29 라 노이즈).

### filing 이 왜 역인가 — 추정이며 확정이 아니다

프로덕션의 filing 은 `55 + FMP 13F/Form4/8-K 델타`다. yfinance 프록시 분기는
**실행되지 않는다** (2026-09-07 라이브 확인: AAPL·DINO·ELV·KDP 모두
`available=True`). 처음에 프록시의 "3개월 신고가 근접 +8" 로 설명했던 것은
틀렸고 여기서 정정한다.

13F 는 분기 데이터이고 분기말 +45일에 공시된다. `_latest_13f_quarter()` 가
집는 분기의 "신규진입 +131곳" 은 최대 4~5개월 전 기관들의 행동이다. 그것을
보고 지금 사는 것은 이미 오른 뒤에 따라 사는 것이라, 5~10일 지평에서
되돌리는 것이 자연스럽다.

데이터 품질도 의심스럽다. 같은 확인에서 AAPL 기관 지분율 **110.3%**, 분기
변화 **+46.34%p** 가 나왔다. 성립할 수 없는 값인데
`ownershipPercentChange > 1.0` 이면 +5 를 주는 규칙이 그대로 쓴다.

**그러나 이 절은 가설이다.** 이번 변경은 이 가설에 기대지 않는다 — 기대는
"filing 의 몫을 줄인다" 까지이고, 13F 규칙 자체는 건드리지 않는다.

## 변경 내용

```
현행   tech .30 + flow .20 + filing .30 + value .20
변경   tech .30 + flow .20 + filing .20 + value .30
```

`calc_total` 의 하드코딩 리터럴을 이름 붙인 모듈 상수로 뺀다. ETF 가 이미
`ETF_TECH_WEIGHT` / `ETF_FLOW_WEIGHT` 로 그렇게 되어 있어 형태를 맞춘다.

**아카이브를 `recompute_history.py --apply` 로 재계산한다.** 백업은
`history_pre_reweight`. 재계산하지 않으면 2026-08-24 flow 축 때와 같은 문제가
난다 — 진입일은 구 척도, 청산 판정일은 신 척도가 되어 `exit_rules.evaluate` 가
서로 다른 자로 잰 값을 비교한다.

**`forward_returns.py` 에 `--by-axis` 를 추가한다.** 트립와이어를 잴 도구다.
값 변경과 같은 변경분에 넣는 것은 의도다 — 판정 도구 없이 값만 바꾸면 나중에
되돌릴지 말지를 정할 근거가 없다.

변경 범위는 이 셋뿐이다. `calc_filing_score` · `calc_value_score` ·
`calc_consensus` · `calc_signal` · `tracks.py` 는 건드리지 않는다.

## 왜 맞바꾸기인가 — 소수점을 데이터에서 읽지 않는다

후보 다섯을 아카이브 축 값으로 재조합해 총점 rho 를 다시 쟀다.

| 가중치 | 5일 전체 (전/후반) | 10일 전체 (전/후반) |
|---|---|---|
| 현행 .30/.20/.30/.20 | -0.0286 (-0.057 / +0.056) | -0.0112 (-0.011 / -0.032) |
| **맞바꿈 .30/.20/.20/.30** | **-0.0124** (-0.042 / +0.067) | **+0.0073** (+0.007 / -0.003) |
| halveF .30/.20/.15/.35 | -0.0047 (-0.035 / +0.073) | +0.0158 (+0.016 / +0.009) |
| 균등 .25/.25/.25/.25 | -0.0170 (-0.044 / +0.063) | +0.0033 (+0.003 / -0.005) |
| filing 제거 .375/.25/0/.375 | +0.0027 (-0.030 / +0.068) | +0.0185 (+0.019 / +0.013) |

**filing 비중을 줄일수록 rho 가 단조 개선된다. 이 순서는 잰 네 칸 전부에서
같다.** 방향에는 근거가 있다.

값을 맞바꾸기로 고른 것은 이 표를 보고 고른 것이 아니다. "일관되게 해로운
축의 몫을 일관되게 이로운 축에 준다" 는 규칙이며, 그 규칙이 부르는 숫자가
0.20/0.30 이다.

halveF(.15/.35)가 네 칸 전부에서 조금 더 좋았다. 그것을 고르지 않는 이유는
**차이가 노이즈와 구분되지 않는데 아카이브를 보고 소수점을 정하는 것이 되기
때문**이다. `exit_total` 45 를 표본 1건으로 고른 것이 지금 판정 불가 상태로
남아 있다. 같은 실수를 반복하지 않는다.

filing 제거(0)를 고르지 않은 이유는 다르다. 13F 가 고쳐지면 정보를 가질 수
있는 축이고, 지금 빼면 남는 것이 value 뿐인데 tech·flow 가 무신호라 사실상
단일 축 도장이 된다. ETF 가 2026-08-22 에 겪은 붕괴와 같은 모양이다.

## 무엇을 기대하면 안 되는가

이 절이 이 문서에서 가장 중요하다.

1. **BUY 개수는 줄지 않는다.** 14일 고유 69 → **71종목**, 하루 평균 20.1 →
   22.1건. 조사를 시작하게 한 불만("BUY 가 너무 많다")은 이 변경으로 **풀리지
   않는다.** 그것은 후보 대 자본의 문제이고 별건이다 — 14일 누적 고유 후보
   69종목에 자본이 감당한 것이 20종목, 현금부족 거절 63건이었다.
2. **총점에 우위가 생기지 않는다.** 10일 rho -0.011 → +0.007 은 "덜 나쁨"
   이지 예측력이 아니다.
3. **5일 지평에서는 어느 가중치든 전·후반 부호가 뒤집힌다.** 후보 다섯 전부
   그렇다. 짧은 지평에서 총점의 방향은 안정적이지 않다.

목적은 하나다 — **일관되게 해로운 입력의 몫을 줄이는 것.** 성적이 좋아진다는
약속이 아니다.

## 무엇을 바꾸지 않는가

- **`min_total` 70 · `exit_total` 60.** 총점 분포가 거의 안 움직인다: 평균
  55.9 → 56.2, p95 71 → 72, 최대 84 → 83. 두 임계의 의미가 유지되므로 같이
  손대면 원인이 섞여 어느 쪽 효과인지 판정할 수 없다.
- **ETF 가중치 (tech .60 / flow .40).** 전 구간으로는 tech +0.162 ·
  flow -0.142 로 두 축이 서로를 지우는 그림이 나왔지만, **기간 분할이
  불가능하다** — 봉 캐시가 09-02 자라 5일 선행이 확보되는 ETF 행이 08-26
  이전뿐이고 후반 표본이 0이다. 단일 창 하나로는 판정하지 않는다.
- **`calc_filing_score` 내부 13F 규칙.** 소급 검증이 불가능한 변경이라
  (아카이브에 시점 공시 데이터가 없다) 앞으로 모을 데이터로만 판정할 수
  있다. 이번 변경과 섞지 않는다.
- **`calc_consensus` 와 축별 70점 기준.** BUY 판정의 합의 조건은 그대로다.

## 측정의 한계 — 과신 금지

- **행이 겹친다.** 같은 종목의 연속일 행이 서로 독립이 아니다. 명목 n 이
  실효 표본보다 훨씬 크므로 rho 의 유의성을 액면대로 읽으면 안 된다. 위
  판정은 "부호가 유지되는가" 까지만 본다.
- **단일 국면.** 아카이브 전 구간이 NEUTRAL 이다 (주식 39,060행 중 39,060).
- **지평 불일치.** 전략은 3개월 보유인데 재는 것은 5~10거래일이다.
- **캐시가 09-02 자다.** 최근 5거래일이 측정에서 빠진다. 10일 후반 표본이
  296행뿐인 것도 이 때문이다.
- **아카이브가 짧다.** 주식 38일(2026-07-31 ~ 09-07).

## 트립와이어

각 줄은 **관측 조건 → 무엇이 틀린 것 → 수정안** 이다. 판정 시점은 아카이브
60일(2026-07-31 시작이므로 **2026-09-29**), 캐시를 갱신한 뒤에 잰다.

**트립와이어를 재려면 도구가 필요하다.** T1~T3 은 축별·총점별 rho 를
요구하는데 지금은 그것을 내는 명령이 없다. 구현에 `forward_returns.py
--by-axis` 를 포함한다 — 이미 캐시와 아카이브를 읽는 스크립트라 새 파일을
만들지 않는다. 이것 없이 값만 바꾸면 **판정할 수 없는 변경**이 되고, 그것이
`exit_total` 45 가 지금 처한 상태다.

### T1. filing rho 가 두 지평 모두 양수로 돌아선다

filing 이 해로운 축이 아니었고, 이번에 잰 음수가 짧은 구간의 우연이었다는
뜻이다.

**수정안:** 가중치를 0.30 으로 되돌린다. 상수 한 줄 + recompute 라 싸다.

### T2. value rho 가 음수로 뒤집힌다

value 에 몫을 더 준 것이 해가 된다. 이 변경의 전제가 무너진다.

**수정안:** 되돌린다. value 가 유일한 양신호였다는 것이 이 변경의 유일한
근거이므로, 그것이 사라지면 근거가 통째로 사라진다.

### T3. 재조합 총점 rho 가 현행 가중치보다 나쁘다

맞바꾸기의 방향 자체가 틀렸다.

**수정안:** 되돌린 뒤, 축 가중치가 아니라 축의 **정의**를 의심한다. 네 축이
전부 무신호라면 가중치를 어떻게 섞어도 총점은 무신호다.

### T4. BUY 가 14일 이동평균으로 하루 30건을 넘는다

분포가 거의 안 움직인다는 가정(평균 +0.3점)이 깨진 것이다.

**수정안:** 이때는 임계값을 본다. 단 `min_total` 을 올리는 것에는 근거가
없다는 이번 조사 결과(총점 70~79 구간이 55~64 구간보다 나은 구석이 없다)를
먼저 다시 읽을 것.

### T5. 아카이브에 두 척도가 섞인다

`recompute_history.py --apply` 를 빠뜨렸거나 일부만 돌았다.

**수정안:** `verify_archive.py` 가 잡는 것과는 다른 종류의 오염이다. 재계산
전후의 total 분포를 비교해 확인하고, 백업(`history_pre_reweight`)에서
되돌린 뒤 다시 돌린다.

## 되돌리기

1. `calc_total` 의 가중치 상수를 원래 값으로.
2. `history_pre_reweight/` 를 `history/` 로 복원, 또는 `recompute_history.py
   --apply` 재실행.

두 단계 다 싸다. 이 문서가 권하는 것은 **되돌리기를 주저하지 않는 것**이다 —
기대 이득이 작으므로 유지할 이유도 그만큼 약하다.

## 측정 재현 방법

이 문서의 숫자를 다시 만들려면:

```
python forward_returns.py --history 'history/*.csv'            # 신호별 값어치
python forward_returns.py --history 'history/*.csv' --by-axis  # 축별·총점 rho (구현 예정)
python backtest.py --track stocks --start-date 2026-08-25 --capital 10000
```

`--by-axis` 는 이 변경과 함께 만든다 (트립와이어 절 참조). 축 값과 n 거래일
선행 수익률의 Spearman 순위상관을 축마다 내고, 기간을 반으로 갈라 부호가
유지되는지 함께 보여야 한다 — 이 문서의 판정이 전부 "부호가 유지되는가" 이기
때문이다.

캐시를 갱신하려면 `python recompute_history.py --refresh` (`--apply` 없이
비교만). 티커 1,685개를 다시 받으므로 rate limit 이 그날 스캔에 영향을 줄 수
있다. 스캔 직후(KST 08:20 이후)에 돌리는 것이 안전하다.

# 스캔 스코어 이력 적재 설계 (0단계)

작성일: 2026-08-18
상태: 승인됨

## 배경

`stock_finder.py`는 매일 KST 06:00에 1,100여 종목을 스코어링해 `dashboard_data.js`를 덮어쓴다.
결과가 매번 덮어써지므로 과거 시점의 스코어가 남지 않고, 따라서 이 스코어에 실제 투자 엣지가
있는지 검증할 방법이 없다.

자동매매 시스템을 올리기 전에 반드시 답해야 하는 질문은 "구현이 되느냐"가 아니라
"이 스코어가 실현수익과 상관이 있느냐"이다. 그 검증에 필요한 원천 데이터를 지금부터 쌓는 것이
이 문서의 범위다.

검증 착수 시점은 데이터 적재 시작일에 종속된다. 3개월 보유 전략이므로, 오늘 시작하면
첫 유의미한 검증은 약 3개월 뒤에 가능하다.

## 목표

1. 매일 전체 유니버스의 스코어와 가격 스냅샷을 영구 보존한다.
2. 나중에 복원 불가능한 값(시가총액, 유니버스 구성원)을 지금 확보한다.
3. 손상된 스캔 결과가 이력에 유입되지 않도록 차단한다.

## 비목표 (의도적 제외)

- **미래수익률 계산 및 조인** — 2단계(백테스트 하네스)의 범위. 여기서는 원천 데이터만 확보한다.
- **매도/청산 로직** — 1단계.
- **브로커 연동** — 4단계.
- `dashboard_data.js` 스키마 변경 — 대시보드 페이로드는 건드리지 않는다.

## 설계 결정

| 항목 | 결정 | 근거 |
|---|---|---|
| 저장 형식 | 일별 CSV, 리포에 커밋 | append-only라 병합 충돌이 없고, git이 텍스트를 잘 압축하며, 기존 CI가 이미 리포에 커밋하는 패턴이라 추가 인프라가 0이다 |
| 적재 범위 | 스코어 + 종가·거래량·ATR·시가총액 | 시총과 유니버스 구성원은 시점이 지나면 복원 불가. 사이징(ATR)과 유동성 필터(거래량)는 백테스트 시 반드시 필요하다 |
| 소급 적재 | 함 (손상본 제외) | git에 스냅샷 23개가 남아 있어 검증 시작점을 3주 앞당길 수 있다 |
| 구현 구조 | `history.py` 모듈 분리 | `stock_finder.py`가 이미 1,500줄이다. 스키마와 기록 책임을 한 곳에 모아 단독 테스트가 가능하게 한다 |

### 검토했으나 채택하지 않은 대안

- **SQLite 단일 파일**: SQL 질의는 편하나 바이너리라 매일 전체가 새 blob으로 저장돼 git 히스토리가
  빠르게 비대해진다. 동시 커밋 시 병합도 불가능하다.
- **Parquet**: 압축률은 좋으나 git diff로 내용 확인이 안 되고 pyarrow 의존성이 추가된다.
  연 40만 행 규모에서는 CSV 대비 실익이 작다.
- **외부 DB(Supabase 등)**: 리포는 안 커지나 CI에 시크릿·네트워크 의존성이 추가되고,
  로컬 오프라인 분석이 불가능해진다.
- **`dashboard_data.js` 후처리로 CSV 생성**: 그 파일에는 가격·ATR·시가총액이 없어 불가능하다.

## 구조

```
history.py              신규 · 스키마 정의 + CSV 기록 (단일 책임)
backfill_history.py     신규 · git 스냅샷 소급 적재 (1회성 스크립트)
stock_finder.py         수정 · 이력 행 추출 후 history.record() 호출
tests/test_history.py   신규 · pytest 3건
history/YYYY-MM-DD.csv  산출물 · 하루 1파일
```

## 스키마

23개 열, 순서 고정:

```
scan_ts_kst, date, ticker, name, market, sector,
bar_date, close, volume, avg_vol20, atr14, market_cap,
tech, macro, filing, value, total, consensus, signal, ev, target, hitl, source
```

| 열 | 설명 |
|---|---|
| `scan_ts_kst` | 스캔 시작 시각 (ISO 8601, KST · `+09:00` 오프셋 명시) |
| `date` | 스캔의 **KST 날짜**. 파일명과 동일 |
| `bar_date` | 스코어링에 사용된 마지막 봉의 **거래소 세션 날짜** (변환하지 않음) |
| `close` | `bar_date`의 종가 |
| `volume` | `bar_date`의 거래량 |
| `avg_vol20` | 최근 20봉 평균 거래량 (유동성 필터용) |
| `atr14` | 14봉 ATR (포지션 사이징·손절폭 산출용) |
| `market_cap` | `info["marketCap"]`. 소급분은 공란 |
| `tech`~`target` | 기존 스코어 필드 |
| `hitl` | 기존 HITL 플래그 |
| `source` | `live` 또는 `backfill` |

### 날짜 기준: KST

스캔 시각 관련 열(`scan_ts_kst`, `date`)과 파일명은 **모두 KST 기준**이다.
스캔은 UTC 21:00에 실행되는데 이는 KST로 익일 06:00이므로, UTC를 쓰면 파일명이 하루
앞선 날짜가 되어 사람이 읽을 때 계속 어긋난다. KST 기준이면 "KST 06:00에 돈 스캔"과
"그날짜 CSV"가 직관적으로 일치한다.

`scan_ts_kst`는 같은 KST 날짜에 여러 번 실행된 경우를 구분한다.

**구현 주의**: CI 러너의 시스템 시간대는 UTC이고 개발 머신은 KST이므로, naive한
`datetime.now()`는 실행 환경에 따라 다른 값을 낸다. 반드시
`datetime.now(timezone.utc).astimezone(timezone(timedelta(hours=9)))`로 명시 변환한다.

#### `bar_date`만 예외인 이유

`bar_date`는 시각이 아니라 거래소 세션의 이름표다. 미국 세션 `2026-08-17`은 KST로
8/17 22:30 ~ 8/18 05:00에 걸쳐 있어 단일 KST 날짜로 환산할 수 없고, 환산하면 거래소가
쓰는 날짜와 어긋나 다른 데이터 소스와 조인이 깨진다. 따라서 `bar_date`는 거래소가
부여한 세션 날짜를 그대로 보존한다 (미국은 ET 기준, 한국은 KST 기준).
수익률 계산은 이 열로 조인한다.

### `source` 열이 필요한 이유

소급분은 `market_cap`이 비어 있다. 구분자가 없으면 나중에 "8월 초에는 시총이 없었다"를
데이터 결측이 아니라 실제 현상으로 오독할 수 있다.

## 데이터 흐름

```
스캔 루프 → _scan_one()이 (대시보드행, 이력행) 튜플 반환
   ↓
완결성 가드 — 수집률 < --min-success 이면 exit 1
   ↓
history/YYYY-MM-DD.csv 기록 (KST 날짜)  ← 가드 통과분만
   ↓
dashboard_data.js 기록
   ↓
CI: git add dashboard_data.js history/
```

가드보다 뒤에 기록하는 것이 핵심이다. 773종목짜리 손상 스캔이 이력에 영구 기록되면
몇 달 뒤 백테스트 결과가 오염되는데, 그 시점에는 원인 추적이 사실상 불가능하다.

같은 KST 날짜에 두 번 실행되면 나중 실행이 파일을 덮어쓴다. 가드를 통과한 결과만
기록되므로 나중 것이 항상 유효하다.

## 소급 적재

`backfill_history.py`가 수행하는 일:

1. `git log --format=%H -- dashboard_data.js`로 스냅샷 커밋을 순회한다.
2. 각 blob에서 `window.LIVE_STOCKS`와 `generated_at`을 파싱한다.
   `generated_at`은 CI 러너에서 생성된 naive UTC 값이므로 UTC로 간주해 KST로 변환한다.
3. 종목 수가 전체 스냅샷 중앙값의 50% 미만인 스냅샷은 손상으로 보고 제외한다.
   현재 데이터에서는 2026-08-03(133종목), 2026-08-18(773종목)이 걸러진다.
4. 등장한 고유 티커에 대해 1년 일봉을 **티커당 1회만** 받는다 (약 1,200회 호출).
   `info`는 받지 않으므로 정규 스캔보다 빠르다.
5. 각 스냅샷 날짜에 해당하는 봉을 잘라 `close`·`volume`·`avg_vol20`·`atr14`를 채운다.
6. `market_cap`은 공란, `source=backfill`로 기록한다.

같은 날짜에 스냅샷이 여러 개면 가장 늦은 것을 채택한다.
이미 존재하는 `history/*.csv`는 덮어쓰지 않는다 (재실행 안전).

## 에러 처리

| 상황 | 처리 |
|---|---|
| 수집률 < `--min-success` | 이력·대시보드 모두 미기록, exit 1 |
| 이력 CSV 기록 실패 | exit 1 (하드 실패) |
| 개별 종목의 가격 필드 결측 | 해당 열만 공란, 행은 기록 |

이력 기록 실패를 하드 실패로 두는 이유는, 조용한 이력 누락이 0단계가 막으려는 바로 그
문제이기 때문이다. 몇 달 뒤 구멍을 발견하면 그 기간은 복구할 수 없다.

개별 종목의 가격 필드 결측을 행 탈락으로 처리하지 않는 이유는, 스코어 자체는 유효하므로
버릴 이유가 없기 때문이다.

## 테스트

리포에 테스트가 없으므로 pytest를 도입하고 3건만 추가한다.

1. **`record()` 왕복** — 기록 후 다시 읽었을 때 열 순서와 값이 보존되는지.
2. **가드 연동** — 수집률 미달 시 CSV가 생성되지 않는지.
3. **소급 파서** — 손상 스냅샷 제외 판정이 의도대로 동작하는지 (중앙값 50% 기준).

`requirements.txt`에 `pytest`를 추가한다. CI 스캔 잡에서는 실행하지 않는다
(스캔은 네트워크 의존적인 장시간 작업이라 테스트와 성격이 다르다).

## 리포 용량 영향

행당 약 120바이트 × 1,103행 = 일 약 130KB, 연 약 47MB(raw).
gzip 압축 후 `.git` 기준 연 15MB 내외로 예상한다. 현재 `.git`은 1.9MB다.
3년 치를 쌓아도 GitHub 권장 한도(1GB) 대비 여유가 있다.

용량이 문제가 되면 연도별로 오래된 CSV를 `.tar.gz`로 묶는 방식을 나중에 검토한다.
지금 도입하지는 않는다.
